Why it is a primitive and not three inputs
The focus order, the keyboard and the meaning of submit belong to the group, not to any field in it. Submit means next gap — the next unfilled well in the group, then the next group — so three gaps are three taps and three numbers with no scrolling back. No control in 1l owns behaviour across siblings.

Keys are 64px, above the 56px minimum: this is a keypad used drunk, and mis-taps here write wrong numbers into a catalog. No letters, no decimal on the ml field, backspace in #b2b6ca. The action key is the group’s only accent: it reads Next gap while gaps remain and Done on the last one.

Call sites — three, one of them new
Scanner review (4i) — the reason it exists. Fields abv / serve / price, gaps sorted to the top of the screen, submit walking them in order.
Custom drink (4f) — strength / serve / price, same three fields, no gaps: the group starts empty and submit walks left to right.
Body stats (4a) — weight / height / age, laid out as the 2×2 grid rather than a well row, but the same keyboard and the same submit-advances behaviour. Adopt it here only if the grid can keep its 28px values.
API shape
<KeypadFieldGroup
  fields={[
    { key: "abv",   unit: "%",  value: 4.6,  max: 60 },
    { key: "serve", unit: "ml", value: 568,  integer: true },
    { key: "price", unit: "£",  value: null },   // null renders the amber gap
  ]}
  onCommit={(key, value) => …}
  onAdvance={() => …}      // called on submit; parent decides the next group
  emptyIsAllowed            // 4i saves with gaps left; 4f does not
/>
No variant keys are removed and nothing existing is replaced — this is additive, so there are no call sites to break. It does not subsume 1l’s single numeric input: one number with a unit toggle stays what it is.
Type floor
Every value the user reads or types is 19px. The 13px unit labels under the wells are the only small type, and they are labels — the answer is never 13px. That holds the floor on the densest screen in the product.
